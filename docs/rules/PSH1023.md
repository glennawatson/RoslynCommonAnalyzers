# PSH1023 — Use a tuple instead of an anonymous type for a local value

| Item | Value |
| --- | --- |
| Category | Allocations |
| Severity | Warning |
| Code fix | Yes (rewrite as a tuple) |

## Cause

A local variable is initialized with an anonymous type, and every use of that local is a member read.

## Rule description

An anonymous type is a class, so every `new { A = ..., B = ... }` is a heap allocation and a
garbage-collector visit later. A tuple carrying the same named members is a struct that lives on the
stack, and it deconstructs, which the anonymous type cannot.

A tuple exposes its elements through the same member syntax, so the reads do not change:

```csharp
// 👎 reported
var pair = new { Left = 1, Right = 2 };
return pair.Left + pair.Right;

// 👍 not reported
var pair = (Left: 1, Right: 2);
return pair.Left + pair.Right;
```

The rule is deliberately narrow, because an anonymous type's class-ness is sometimes load-bearing. It
reports only when:

- The anonymous type initializes a local declared in a block.
- Every use of that local is a member read (`pair.Left`). The moment the value is returned, passed as an
  argument, stored, or captured, its type is part of a contract this analyzer cannot see all of — a query
  provider or serializer may depend on it being a reference type — and the rule stays silent.
- It has at least two members. A one-member wrapper is not worth churn.
- Every member has a name a tuple can carry, either written (`A = x`) or inferred (`source.Width`).

## How to fix violations

Write the tuple: `(Left: 1, Right: 2)`. The member reads keep working unchanged.

## Performance

The callback is registered on the anonymous object creation itself, which is already rare, so the escape
scan runs only for a construct that is a candidate. The scan walks the declaring block once through the
shared descendant helper rather than materializing an iterator.
