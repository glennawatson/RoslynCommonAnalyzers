# PSH1317 — Pass the cancellation token to the call that accepts one

| Item | Value |
| --- | --- |
| Package | PerformanceSharp.Analyzers |
| Category | Concurrency |
| Severity | Warning |
| Code fix | Yes (supports Fix All) |
| Default | Enabled |

## Cause

A cancellation token is in scope, and a call that could carry it does not.

```csharp
// 👎 reported
public async Task<string> LoadAsync(HttpClient client, string url, CancellationToken cancellationToken)
{
    await Task.Delay(100);                     // PSH1317: an overload takes a token
    using var response = await client.GetAsync(url);  // PSH1317: an overload takes a token
    return await response.Content.ReadAsStringAsync();
}
```

## Rule description

Cancellation only works if the token reaches the bottom of the call chain. A call that drops it is where
cancellation stops: everything below that line runs to completion after the caller has already given up.
The thread-pool worker stays occupied, the socket or file handle stays open, the database keeps executing
the query — and the result is discarded the moment it finally arrives. Under a request timeout or a
shutdown, that is work the process pays for twice: once for the abandoned call, once for the retry.

The method that would receive the token is proved, never guessed. Two shapes qualify:

- the called method **already has a cancellation token parameter** and the call left it at its default, or
- the called method has none and **a sibling overload takes one**.

A sibling qualifies only when it is declared on the same type, agrees on staticness, returns exactly the
same type, and accepts the very arguments already written — its parameters, minus the token, must lead
with the called method's parameters and add nothing that is not optional. So a framework that has no
cancellable form of a call is never reported for it, which matters because the token-accepting overload of
a method is often newer than the method itself.

### Where the token comes from

The token is a parameter of the nearest enclosing function — the method, or the lambda or local function
the call sits inside. A lambda's own token parameter wins over the method's, since it is the one the caller
of that lambda is driving.

### What is reported

- A call with a token parameter that was skipped, including one skipped past other optional parameters.
- A call whose type carries an overload that takes a token and accepts the same arguments.

### What is not reported

- A call that **already passes a token** — including an explicit `CancellationToken.None`. Passing the
  empty token is how you say "this one is deliberately not cancellable", and the rule respects it.
- A call site with **no token in scope**, and one inside a `static` lambda or local function, which cannot
  capture the enclosing method's token.
- A token declared **by reference** (`in`, `ref`, `out`), which a nested function cannot capture.
- An overload that would need **another argument**, returns something else, or is not accessible from the
  call site.
- A **generic** method, and an **extension** method called with the receiver before the dot, when the token
  lives on a separate overload rather than on the method being called. Their parameter lists do not line up
  with the arguments as written, so the rule stays silent instead of suggesting a call it cannot prove.
  An extension method with its own optional token parameter — the usual shape — is reported normally.
- Object creation. Only calls are inspected.

An implicitly typed lambda parameter carries no type to match against, so a token that arrives only as
`(item, token) => …` is not seen; a call inside that lambda is reported against the enclosing method's
token if there is one, and left alone otherwise.

## How to fix violations

Pass the token. The code fix inserts it in its parameter's own position, and names it when the slot is
reached only past a skipped optional parameter:

```csharp
// 👍 — cancellation reaches the bottom
await Task.Delay(100, cancellationToken);
using var response = await client.GetAsync(url, cancellationToken);
await sender.SendAsync(message, cancellationToken: cancellationToken);
```

The rewritten call is speculatively bound before the fix is offered, so an argument list that would pick a
different overload — or not compile — is never suggested. A call reached through a conditional access
(`target?.Send(…)`) is reported but not fixed automatically: the detached call cannot be rebound to check.

If a call genuinely should outlive its caller — a fire-and-forget audit write, a cleanup that must finish
even during shutdown — pass `CancellationToken.None` explicitly. That silences the rule and records the
decision for the next reader.

## Performance

The clean path is syntactic. Each call walks its parent chain for a parameter declared as a
`CancellationToken` and stops at the enclosing member; a call with nothing to pass never reaches the
semantic model. Only after a token is found is the call bound and its type searched for a cancellable
overload, and that search is memoized per method symbol, so a file that calls the same method a hundred
times pays for it once. The whole rule registers nothing when `System.Threading.CancellationToken` does
not resolve.
