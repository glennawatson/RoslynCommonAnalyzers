# PSH1318 — Validate options asynchronously instead of blocking

| Item | Value |
| --- | --- |
| Category | Concurrency |
| Severity | Warning |
| Code fix | No |
| Applies to | Projects referencing `IAsyncValidateOptions<T>` |

## Cause

A type implementing `IValidateOptions<T>` blocks a thread on asynchronous work inside `Validate`.

```csharp
public sealed class ConnectionValidator : IValidateOptions<ConnectionOptions>
{
    public ValidateOptionsResult Validate(string? name, ConnectionOptions options)
    {
        _probe.CanConnectAsync(options.Endpoint).Wait();
        return ValidateOptionsResult.Success;
    }
}
```

## Rule description

`IValidateOptions<T>.Validate` is synchronous, so a validator that needs to reach a database or a
remote service has nowhere to await and blocks the calling thread instead.

Options are usually validated while the host starts, on a thread pool that is simultaneously serving
everything else starting up. Each blocked validator removes a worker for the length of the round trip,
and several of them together can exhaust the pool and stall startup outright — the failure looks like
a hang rather than like a slow validator.

`IAsyncValidateOptions<T>` gives validation a real asynchronous entry point, so the thread is released
while the work is in flight:

```csharp
// 👍
public sealed class ConnectionValidator : IAsyncValidateOptions<ConnectionOptions>
{
    public async ValueTask<ValidateOptionsResult> ValidateAsync(string? name, ConnectionOptions options, CancellationToken cancellationToken)
    {
        await _probe.CanConnectAsync(options.Endpoint, cancellationToken);
        return ValidateOptionsResult.Success;
    }
}
```

## What is not reported

- A validator that does no asynchronous work. Validation that only inspects the options object should
  stay synchronous.
- A type that already implements `IAsyncValidateOptions<T>`. Keeping a synchronous path alongside it
  is a deliberate choice, and the async entry point exists.
- A `Validate` method on a type that does not implement `IValidateOptions<T>`.
- Anything at all when `IAsyncValidateOptions<T>` does not resolve in the compilation.

The blocking calls themselves are reported separately by **PSH1315**, wherever they appear. This rule
reports once, on the method, because the finding is about which interface the type implements rather
than about any one wait.

## How to fix violations

Implement `IAsyncValidateOptions<T>` and move the body into `ValidateAsync`, awaiting the work instead
of blocking on it. Register the validator the same way; the options infrastructure resolves the
asynchronous interface when it is present.
