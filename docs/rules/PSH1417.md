# PSH1417 — Do not compute an expensive argument for an assertion

**Category:** ApiSelection
**Severity:** Warning
**Code fix:** None.

## Cause

An argument after the first argument of `Debug.Assert` contains a method call
or object construction. These are normally message arguments, and building
them on every passing assertion wastes work. On frameworks without deferred
interpolated assertion messages, nonconstant interpolated messages are also
reported.

The first argument, normally the condition, is not checked. Constants, including
`nameof(...)`, are excluded. A property read by itself is not reported. Direct
interpolated messages are excluded when the framework provides
`Debug.AssertInterpolatedStringHandler`.

This cost applies when `DEBUG` is defined. Without `DEBUG`, the compiler removes
the `Debug.Assert` call and the evaluation of its arguments.

## Example

Before:

```csharp
using System.Collections.Generic;
using System.Diagnostics;

public class Validator
{
    public void Check(List<string> items) =>
        Debug.Assert(items.Count > 0, string.Join(",", items));
}
```

After, with C# 10 or later and .NET 6 or later:

```csharp
using System.Collections.Generic;
using System.Diagnostics;

public class Validator
{
    public void Check(List<string> items) =>
        Debug.Assert(items.Count > 0, $"{string.Join(",", items)}");
}
```

The interpolated message above is built only when the assertion fails.

## How to fix violations

Pass the interpolated string directly as the message so the deferred-message
overload can be used. Storing it in a string variable first still does the work
before the assertion. On older frameworks, use a constant message or move
message construction into a failure branch guarded by `#if DEBUG`.

There is no automatic code fix.

## Configuration

The rule is enabled at `warning` by default. It has no rule-specific options.

```editorconfig
[*.cs]
dotnet_diagnostic.PSH1417.severity = warning
```

Severity values are `none`, `silent`, `suggestion`, `warning`, and `error`.

## When to suppress

Suppress when the message call is cheap and keeping it makes the assertion
clearer, or when the cost is acceptable in a rarely reached debug path. Work
needed for program behavior belongs outside the assertion, because a build
without `DEBUG` removes it.
