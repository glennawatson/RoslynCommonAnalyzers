# SES1006 — Persisted Data Protection keys must be encrypted at rest

**Category:** Cryptography  
**Severity:** Warning  
**Code fix:** None.

## Cause

ASP.NET Core Data Protection is configured to store its keys in an explicit
repository without a recognized call to encrypt them. Choosing a storage location
disables automatic encryption of the stored keys. Anyone who can read unprotected
keys can decrypt protected data or forge authentication cookies.

The rule checks these extension methods on `IDataProtectionBuilder`:

- `PersistKeysToFileSystem`
- `PersistKeysToDbContext`
- `PersistKeysToAzureBlobStorage`
- `PersistKeysToStackExchangeRedis`
- `PersistKeysToRegistry`

It accepts `ProtectKeysWithCertificate`, `ProtectKeysWithDpapi`,
`ProtectKeysWithDpapiNG`, or `ProtectKeysWithAzureKeyVault` in the same call chain.
Inside a lambda, it accepts a protection call anywhere in that lambda's body.
It does not check that the calls use the same builder instance or that the
protection call runs on every path.

Outside a lambda, separate statements are checked separately. Protection configured
in another statement or helper method can therefore still leave a warning. The
rule reports nothing when ASP.NET Core Data Protection is not referenced.

## How to fix violations

Bad:

```csharp
using System.IO;
using Microsoft.AspNetCore.DataProtection;
using Microsoft.Extensions.DependencyInjection;

public static class KeyStorage
{
    public static void Configure(IServiceCollection services, DirectoryInfo directory)
    {
        services.AddDataProtection().PersistKeysToFileSystem(directory);
    }
}
```

Choose a protection method for your deployment and apply it to the same builder:

```csharp
using System.IO;
using System.Security.Cryptography.X509Certificates;
using Microsoft.AspNetCore.DataProtection;
using Microsoft.Extensions.DependencyInjection;

public static class KeyStorage
{
    public static void Configure(
        IServiceCollection services, DirectoryInfo directory, X509Certificate2 certificate)
    {
        services.AddDataProtection()
            .PersistKeysToFileSystem(directory)
            .ProtectKeysWithCertificate(certificate);
    }
}
```

Every application instance that reads these keys needs access to the certificate's
private key. DPAPI options require Windows; a key vault needs its key identifier
and access permissions. There is no automatic code fix because the protection
method and credentials depend on your deployment.

## Configuration

The rule is enabled at `warning` by default. It has no rule-specific options.

```ini
[*.cs]
dotnet_diagnostic.SES1006.severity = warning
```

Severity values are `error`, `warning`, `suggestion`, `silent`, and `none`.

## When to suppress

Suppress when you have verified that the same key ring is encrypted by a custom
protector or by configuration elsewhere. Explain where that protection is applied.
A shared storage location alone does not protect the keys.
