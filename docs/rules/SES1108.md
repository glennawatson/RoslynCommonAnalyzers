# SES1108 — Do not accept every server certificate from a custom callback

**Category:** Transport  
**Severity:** Warning  
**Default:** Enabled

## Cause

`HttpClientHandler.ServerCertificateCustomValidationCallback` is assigned a
callback that returns `true` for every certificate. This accepts expired,
untrusted, and wrong-host certificates, allowing an attacker to impersonate the server.

The rule reports a lambda whose result is the literal `true`, or a block lambda
or anonymous method with at least one return and all its return values written as
`true`. It also checks methods and local functions passed as callbacks when their
body is available in the project's source. Parentheses around `true` are allowed.

## Example

Bad:

```csharp
using System.Net.Http;

var handler = new HttpClientHandler
{
    ServerCertificateCustomValidationCallback =
        (message, cert, chain, errors) => true
};
using var client = new HttpClient(handler);
```

Corrected: remove the callback to use the platform's certificate validation.

```csharp
using System.Net.Http;

using var client = new HttpClient();
```

If custom validation is required, reject certificates that fail your checks. For
example, a callback returning `errors == SslPolicyErrors.None` checks the reported
certificate errors and is not flagged.

No code fix is available; choose whether to remove the callback or implement custom validation.

## What is not reported

- Callbacks with a return value other than the literal `true`.
- Delegate variables and methods whose body is only available in a referenced library.
- `HttpClientHandler.DangerousAcceptAnyServerCertificateValidator`, which is covered
  by [SES1102](SES1102.md).

A callback that is not reported can still be unsafe. The rule does not establish
that custom certificate checks are correct.

## Configuration

```ini
[*.cs]
dotnet_diagnostic.SES1108.severity = warning
```

The default is `warning`. Allowed severities are `error`, `warning`, `suggestion`,
`silent`, and `none`. There are no rule-specific options.

## When to suppress

Suppress a callback only in an isolated test that deliberately accepts invalid
certificates. Keep it out of production configuration. For development services,
prefer trusting a development certificate instead of accepting every certificate.
