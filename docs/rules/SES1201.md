# SES1201 — Do not hard-code secrets in source

**Category:** Secrets  
**Severity:** Warning  
**Default:** Enabled

## Cause

A string literal matches a known credential format. Secrets in source can be read
from the repository and the built application. The rule checks the text wherever
the literal appears; the field, variable, or parameter name does not matter.

Recognized formats include:

- Keys beginning with `sk-`, `AKIA`, or `AIza`.
- Tokens beginning with `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `xoxb-`, `xoxa-`,
  `xoxp-`, `xoxr-`, or `xoxs-`.
- Private-key text containing a `-----BEGIN ... PRIVATE KEY-----` header.
- `SharedAccessKey=` or `AccountKey=` followed by a key body.
- A `Password=` or `Pwd=` value of at least four characters in text containing
  `Server=`, `Data Source=`, `Initial Catalog=`, or `Host=`.

These prefixes and markers are case-sensitive. Key formats have minimum lengths
and reject bodies with too few different characters or long repeated runs.
This is a format check, not a test of whether the credential is active.

## Example

Bad, using a test value that matches a credential format:

```csharp
public class Settings
{
    public string GetAccessKey() => "AKIA2E4RJKL7MNPQ6XYZ";
}
```

Corrected:

```csharp
using System;

public class Settings
{
    public string GetAccessKey() =>
        Environment.GetEnvironmentVariable("AWS_ACCESS_KEY_ID")
        ?? throw new InvalidOperationException("Access key is not configured.");
}
```

Use environment variables, development user secrets, or a managed secret store.
Keep secret values out of committed configuration files. Revoke and replace any
real secret that has been committed or distributed.

No code fix is available; choose where the application will read its secrets.

## What is not reported

Ordinary text, public certificate blocks, strings containing both `<` and `>`,
and short or repeated-character key bodies are not reported. Connection-string
password placeholders such as `changeme`, `password`, and `example` are excluded.
Do not treat these exclusions as a way to store real secrets safely.

## Configuration

```ini
[*.cs]
dotnet_diagnostic.SES1201.severity = warning
securitysharp.SES1201.allow_documentation_examples = false
```

The default severity is `warning`. Allowed severities are `error`, `warning`,
`suggestion`, `silent`, and `none`.

| Key | Values | Default |
| --- | --- | --- |
| `securitysharp.SES1201.allowed_example_secrets` | Comma-separated exact literal values | Empty |
| `securitysharp.allowed_example_secrets` | Same; fallback when the rule-specific key is absent | Empty |
| `securitysharp.SES1201.allow_documentation_examples` | `true` or `false` | `false` |
| `securitysharp.allow_documentation_examples` | Same; fallback when the rule-specific key is absent | `false` |

The rule-specific key takes priority, including when it is empty or invalid.
An invalid Boolean value acts as `false`.

For published sample values, prefer an exact list:

```ini
[*.cs]
securitysharp.SES1201.allowed_example_secrets = AKIAIOSFODNN7EXAMPLE, AKIAI44QH8DHBEXAMPLE
```

Entries match the whole literal, case-sensitively. Surrounding whitespace is
trimmed and empty entries are ignored. Commas separate entries; a value containing
a comma cannot be listed as one entry.

Setting `allow_documentation_examples = true` excludes any otherwise matching
literal containing `EXAMPLE`, case-insensitively, anywhere in the text. A real
credential can contain that word, so an exact list is safer. These settings also
affect [SES1707](SES1707.md), which checks secrets in browser code.

## When to suppress

Suppress a specific literal that is a verified fake credential used in a test or
documentation. Prefer the exact example list when the same sample appears more
than once. Do not suppress a real secret; move it out of source and replace it.
