# SES1405 — A MessagePack typeless deserializer must not reconstruct arbitrary types from untrusted input

| Item | Value |
| --- | --- |
| Package | SecuritySharp.Analyzers |
| Category | Serialization |
| Severity | Warning |
| Code fix | No |
| Default | Enabled |

## Cause

The code calls `MessagePackSerializer.Typeless.Deserialize` or `DeserializeAsync`,
or refers to either of these resolver instances:

- `MessagePack.Resolvers.TypelessObjectResolver.Instance`.
- `MessagePack.Resolvers.TypelessContractlessStandardResolver.Instance`.

Typeless MessagePack data carries .NET type names. Reading it can create the types
named by the sender and run their construction or deserialization code.

## Example

Reported:

```csharp
using MessagePack;

public static class Messages
{
    public static object Read(byte[] data) =>
        MessagePackSerializer.Typeless.Deserialize(data);
}
```

Read into a known contract type:

```csharp
using MessagePack;

[MessagePackObject]
public sealed class Payload
{
    [Key(0)]
    public int Id { get; set; }
}

public static class Messages
{
    public static Payload Read(byte[] data) =>
        MessagePackSerializer.Deserialize<Payload>(data);
}
```

## How to fix violations

There is no automatic code fix.

Choose the expected contract type and use typed deserialization with a resolver
that does not support arbitrary type names. Check shared serializer options too:
using `Deserialize<T>` does not remove a typeless resolver configured elsewhere.
Changing the contract can require changes to the writer and to stored messages.

## What is not reported

A typed `MessagePackSerializer.Deserialize<T>` call is not reported. A typeless
resolver reference is reported where `.Instance` appears, even if it is stored in
a variable; later uses of that variable are not reported again.

Unrelated types with the same names are ignored. The rule reports nothing when the
MessagePack typeless APIs and resolvers are unavailable.

## Configuration

```ini
[*.cs]
dotnet_diagnostic.SES1405.severity = warning
```

The rule is enabled by default as a warning. There are no
rule-specific options. Severity values are `none`, `silent`, `suggestion`, `warning`,
and `error`. See [configuration](../CONFIGURATION.md).

## When to suppress

Suppress only when typeless compatibility is required and every payload comes from
a trusted source that untrusted users cannot modify. Do not use this exception for
request bodies, uploads, or writable shared storage.
