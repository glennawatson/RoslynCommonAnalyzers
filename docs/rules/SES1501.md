# SES1501 — A CORS policy must not allow credentials together with any origin

| Item | Value |
| --- | --- |
| Package | SecuritySharp.Analyzers |
| Category | WebHardening |
| Severity | Warning |
| Code fix | No |
| Default | Enabled |

## Cause

ASP.NET Core CORS configuration calls both `AllowAnyOrigin()` and
`AllowCredentials()`. CORS controls which browser origins may read a response from
another origin. An origin is the scheme, host, and port of a site.

Browsers reject credentialed responses that allow the wildcard origin `*`.
ASP.NET Core also rejects this combination, so the policy can fail at runtime.

The rule reports `AllowCredentials()` when it finds both calls in a chain or within
the same configuration callback, in either order.

## Example

Reported:

```csharp
using Microsoft.AspNetCore.Cors.Infrastructure;

public static class CorsConfiguration
{
    public static void Configure(CorsOptions options) =>
        options.AddPolicy("api", policy =>
            policy.AllowAnyOrigin().AllowCredentials());
}
```

Allow credentials for specific trusted origins:

```csharp
using Microsoft.AspNetCore.Cors.Infrastructure;

public static class CorsConfiguration
{
    public static void Configure(CorsOptions options) =>
        options.AddPolicy("api", policy =>
            policy.WithOrigins("https://trusted.example").AllowCredentials());
}
```

## How to fix violations

There is no automatic code fix.

Use `WithOrigins(...)` with the sites that require credentials. For a public API
that does not need credentials, remove `AllowCredentials()` instead.

## What is not reported

`AllowAnyOrigin()` without credentials and credentials with specific origins are
not reported. Calls in separate policy callbacks are not combined. Separate
statements outside a callback are also not combined, even if they change the same
builder.

Within a callback, the rule does not check whether both calls use the same builder
or run on the same execution path. It reports nothing when ASP.NET Core's
`CorsPolicyBuilder` is unavailable.

## Configuration

```ini
[*.cs]
dotnet_diagnostic.SES1501.severity = warning
```

The rule is enabled by default as a warning. There are no
rule-specific options. Severity values are `none`, `silent`, `suggestion`, `warning`,
and `error`. See [configuration](../CONFIGURATION.md).

## When to suppress

Suppress when the calls in one callback configure different builders or mutually
exclusive paths, and you have verified that no resulting policy allows both any
origin and credentials. Do not suppress an actual policy with both settings.
