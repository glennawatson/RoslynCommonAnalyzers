# SES1508 — A validation method must not fail open

**Category:** WebHardening
**Severity:** Warning
**Code fix:** No code fix is available.

## Cause

A validation method catches an exception and returns success. This is called
failing open: a check that could not finish is treated as a passed check.

The rule reports the `catch` when all these conditions hold:

- The method or local function returns `bool`, `Task<bool>`, or `ValueTask<bool>`.
  Its name starts with `Validate`, `Verify`, `Authenticate`, `Authorize`,
  `Check`, `IsValid`, `IsAuthentic`, or `Ensure`, with that capitalization.
- It uses a bare `catch`, catches `System.Exception`,
  `System.Security.Cryptography.CryptographicException`, or
  `System.Security.Authentication.AuthenticationException`, or catches a type
  whose name ends in `SecurityTokenException`.
- The catch only returns `true` or `Task.FromResult(true)`/
  `ValueTask.FromResult(true)`. An empty catch followed immediately by such
  a return is also reported. Empty statements do not affect this check.

## Example

Bad:

```csharp
public class InputValidator
{
    public bool ValidateInput(string value)
    {
        try
        {
            return value.Length > 0;
        }
        catch (System.Exception)
        {
            return true;
        }
    }
}
```

Corrected:

```csharp
public class InputValidator
{
    public bool ValidateInput(string value)
    {
        try
        {
            return value.Length > 0;
        }
        catch (System.Exception)
        {
            return false;
        }
    }
}
```

Return failure when the check cannot finish. Let the exception propagate if
the caller must distinguish invalid input from an unavailable check.

## What is not reported

The rule does not report catches inside lambdas, other method names or return
types, other exception types, or catches that log or perform another operation
before returning. Adding a log statement does not make returning success safe.

## Configuration

Enabled by default. The package default and recommended profile use `warning`.
There are no rule-specific options.

```editorconfig
[*.cs]
dotnet_diagnostic.SES1508.severity = warning
```

Severity accepts `error`, `warning`, `suggestion`, `silent`, `none`, or `default`.
See [Configuration](../CONFIGURATION.md) for details.

## When to suppress

Suppress when the method is an optional, non-security check and returning `true`
after the exception is its intended contract. Do not suppress a check that
controls access merely because its provider can fail.
