# SES1515 — Restrict permissive Content-Security-Policy sources

## Cause

A literal Content Security Policy permits an unrestricted capability through an
effective source list. The diagnostic names that directive and capability.

| Effective directive | Reported permission |
| --- | --- |
| `script-src`, `script-src-elem` | Unrestricted inline scripts or scripts from arbitrary network hosts |
| `script-src-attr` | Unrestricted inline script attributes |
| `script-src` | JavaScript evaluation from strings through `'unsafe-eval'` |
| `style-src`, `style-src-elem` | Unrestricted inline styles or styles from arbitrary network hosts |
| `style-src-attr` | Unrestricted inline style attributes |
| `object-src` | Embedded objects from arbitrary network hosts |
| `base-uri` | Base URLs from arbitrary origins |

A standalone `*` permits arbitrary network hosts. Host patterns such as
`*.example.com` and `https://*` are outside this rule's wildcard check.
Sources in unrelated directives, such as `img-src` or `connect-src`, do not
change a script diagnostic.

Resource-specific directives override their fallbacks. `script-src-elem` and
`script-src-attr` fall back to `script-src`; the matching style directives fall
back to `style-src`. Missing script, style, and object directives fall back to
`default-src`. `base-uri` has no `default-src` fallback. If a directive occurs
more than once, the first occurrence applies. Directive names ignore case.

Comma-separated policies are applied together. A permissive source is not reported
when another policy in the same literal restricts that capability.

The rule checks literal values in CSP header assignments and two-argument calls
such as `headers.Add("Content-Security-Policy", value)`. Standalone literals
beginning with a recognized directive are also checked.

## How to fix violations

Restrict the capability named in the diagnostic. For example, remove unrestricted
inline script execution and list the script origins the page needs:

```csharp
// Permits unrestricted inline scripts.
headers["Content-Security-Policy"] = "script-src 'self' 'unsafe-inline'";

// Permits external scripts from this origin.
headers["Content-Security-Policy"] = "script-src 'self'";
```

If the page needs inline scripts or styles, use a content hash or an unpredictable
nonce generated for each response. Update the corresponding script or style
elements as well as the policy.

Allowing inline styles does not allow inline scripts. Some applications require
inline styles; [Microsoft's Power Pages guidance](https://learn.microsoft.com/en-us/power-pages/security/manage-content-security-policy)
uses a policy that permits them while restricting scripts. Review that CSS
permission separately instead of removing a required style source indiscriminately.

There is no automatic code fix.

## Nonces, hashes, and browser support

The rule evaluates modern CSP3 source semantics:

- A syntactically valid nonce or hash source makes `'unsafe-inline'` ineffective
  within the same source list.
- `'strict-dynamic'` makes `'unsafe-inline'` and host wildcards ineffective for
  scripts. It does not provide that exemption for styles.
- `'unsafe-eval'` remains effective alongside nonces, hashes, and
  `'strict-dynamic'`.
- `'wasm-unsafe-eval'` permits WebAssembly compilation without enabling general
  JavaScript string evaluation and is not reported.

A nonce or hash in one directive does not protect a different directive.
Malformed nonce and hash sources do not grant an exemption.

Older browsers can interpret compatibility sources differently, especially when
they do not support nonces or `'strict-dynamic'`. Review those fallback sources
against the browser versions you support. See the
[CSP reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)
and Microsoft's [Blazor CSP guidance](https://learn.microsoft.com/en-us/aspnet/core/blazor/security/content-security-policy).

## Report-only policies and comparisons

A `Content-Security-Policy-Report-Only` header records violations without enforcing
the policy. Its diagnostic describes what the directive would allow if enforced.
It does not mean an enforced baseline policy has been weakened. Microsoft documents
[using both headers together](https://learn.microsoft.com/en-us/power-pages/security/manage-content-security-policy#test-with-report-only-mode).

Reference text in supported TUnit, xUnit, NUnit, MSTest, FluentAssertions, and
Shouldly assertions is excluded. String equality operators and comparison methods
such as `Contains`, `Equals`, and `StartsWith` are excluded too. An unsafe
header assignment inside a comparison or assertion remains reportable.

The rule examines individual string literals. It does not assemble interpolated
or concatenated policies, combine separate CSP headers, or verify that a nonce is
unpredictable or a hash matches an element. A clean result is not a complete CSP
security review.

## Configuration

Enabled by default as a warning. There are no rule-specific options.

```ini
[*.cs]
dotnet_diagnostic.SES1515.severity = warning
```

Severity values are `error`, `warning`, `suggestion`, `silent`, `none`, and `default`.

## When to suppress

Suppress a specific diagnostic when the named permission is deliberate and has
been reviewed, such as inline styles required by a UI framework. A fixture or
documentation literal outside a recognized comparison can also be suppressed.
Keep the exemption specific to that use.
