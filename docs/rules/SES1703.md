# SES1703 — Authorize on a non-routable component enforces nothing

## Cause

A concrete class derived from Blazor's `ComponentBase` has `[Authorize]` but
no `[Route]` on the same class declaration. Attributes derived from
`AuthorizeAttribute` also count.

Blazor's authorization routing checks a page reached through a route. It does
not enforce `[Authorize]` when a parent renders a child component directly.
Adding the attribute to that child does not protect its content.

## How to fix violations

If the component is intended to be a page, give it a route:

```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Components;

// Before: this component has no route.
[Authorize]
public class AccountPanel : ComponentBase
{
}

// After: this page can be checked by authorization routing.
[Authorize]
[Route("/account")]
public class AccountPage : ComponentBase
{
}
```

Use `AuthorizeRouteView` in the router to enforce page authorization. In Razor,
`@page` declares a route. For a child component, move the policy to its routed
host or use `AuthorizeView` around the protected content, then remove the
misleading attribute from the child. Protect server operations separately;
hiding content does not authorize an API request.

There is no automatic code fix.

## What is not reported

Abstract components, classes derived from `LayoutComponentBase`, and types
that are not Blazor components are excluded. These exclusions do not make
`[Authorize]` enforce itself on a layout or child component.

The rule checks authorization and route attributes on the same declaration.
A route on another partial declaration or an inherited route can therefore
require review when a diagnostic appears.

## Configuration

Enabled by default as a warning.

```ini
[*.cs]
dotnet_diagnostic.SES1703.severity = warning
securitysharp.SES1703.exempt_types = App.Components.TrustedPanel
```

Severity values are `error`, `warning`, `suggestion`, `silent`, `none`, and `default`.

`securitysharp.SES1703.exempt_types` accepts comma-separated component type
names and defaults to an empty list. If it is absent, `securitysharp.exempt_types`
supplies the project-wide list, also empty by default. A rule-specific list,
including an empty one, overrides the project-wide list.

Names are case-sensitive and can be simple names such as `TrustedPanel` or
fully qualified names such as `App.Components.TrustedPanel`. An entry exempts
the named type, not all its subclasses. See
[configuration guidance](../CONFIGURATION.md).

## When to suppress

Suppress or exempt a component when custom infrastructure actually enforces
its authorization attribute, or when a route elsewhere makes the diagnostic
inapplicable. Document that enforcement; the attribute alone is not enough.
