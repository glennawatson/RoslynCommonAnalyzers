# SST1406 — Debug.Fail should provide message text

| Item | Value |
| --- | --- |
| Category | Maintainability |
| Severity | Warning |
| Code fix | No |
| Default | Enabled |

## Cause

A `System.Diagnostics.Debug.Fail` call passes an empty or whitespace string literal
as its first argument. A message tells the person investigating the failure what
went wrong. A detailed message in the second argument does not replace the first.

The rule checks calls written with a type name, such as `Debug.Fail(...)`.
It does not inspect unqualified `Fail(...)` calls imported with `using static`,
or determine whether a variable or expression produces empty text.

## Example

Bad:

```csharp
using System.Diagnostics;

public class Processor
{
    public void ReportUnexpectedState() => Debug.Fail("");
}
```

Corrected:

```csharp
using System.Diagnostics;

public class Processor
{
    public void ReportUnexpectedState() => Debug.Fail("Unexpected processing state.");
}
```

## How to fix violations

Replace the empty text with a message describing the failure.

There is no automatic code fix.

## Configuration

There are no rule-specific options. The rule is enabled as a warning by default.

```editorconfig
[*.cs]
dotnet_diagnostic.SST1406.severity = warning
```

Severity values are `error`, `warning`, `suggestion`, `silent`, and `none`.

## When to suppress

Suppress for a temporary debugger stop when the surrounding context already explains the failure. Keep a useful message in checks that remain in maintained code.
