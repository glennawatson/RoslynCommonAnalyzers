# SST1620 — Type parameter documentation should match the type parameters

| Item | Value |
| --- | --- |
| Category | Documentation |
| Default severity | Warning |
| Code fix | No |

## Cause

A `<typeparam>` element names a type parameter that the documented type or
member does not declare. The comparison is case-sensitive. A method's
`<typeparam>` elements must name its own type parameters, not those of its
containing class.

Comments with a top-level `<inheritdoc>` are skipped. A missing `name` attribute
is handled by [SST1621](SST1621.md).

## How to fix violations

Correct the name if the element describes a real type parameter. Remove it if
the type parameter was removed or the text belongs elsewhere.

Bad:

```csharp
public class Worker
{
    /// <summary>Does work for the selected type.</summary>
    /// <typeparam name="T">The type to process.</typeparam>
    /// <typeparam name="X">Extra.</typeparam>
    public void Run<T>() { }
}
```

Corrected:

```csharp
public class Worker
{
    /// <summary>Does work for the selected type.</summary>
    /// <typeparam name="T">The type to process.</typeparam>
    public void Run<T>() { }
}
```

There is no code fix.

## Configuration

Enabled by default as a warning. The example changes it to an error.
There are no rule-specific options.

```ini
[*.cs]
dotnet_diagnostic.SST1620.severity = error
```

Severity values are `error`, `warning`, `suggestion`, `silent`, and `none`.
Use `none` to disable the rule. See [configuration](../CONFIGURATION.md).

## When to suppress

Suppression is rarely useful: an incorrect name cannot document a type parameter.
Correct or remove the element instead of keeping stale documentation.
