# SST1622 — Type parameter documentation should have text

| Item | Value |
| --- | --- |
| Category | Documentation |
| Default severity | Warning |
| Code fix | No |

## Cause

A type parameter has a matching `<typeparam>` element with no descriptive text.
Empty elements, self-closing elements, and elements containing only whitespace
are reported. Comments with a top-level `<inheritdoc>` are skipped.

A missing element is handled by [SST1618](SST1618.md). Its code fix inserts an
empty element, so this rule can appear after you accept that fix.

## How to fix violations

Explain the type parameter's role or any requirements callers need to know.

Bad:

```csharp
public class Worker
{
    /// <summary>Does work for the selected type.</summary>
    /// <typeparam name="T"></typeparam>
    public void Run<T>() { }
}
```

Corrected:

```csharp
public class Worker
{
    /// <summary>Does work for the selected type.</summary>
    /// <typeparam name="T">The type to process.</typeparam>
    public void Run<T>() { }
}
```

There is no code fix.

## Configuration

Enabled by default as a warning. The example changes it to an error.
There are no rule-specific options.

```ini
[*.cs]
dotnet_diagnostic.SST1622.severity = error
```

Severity values are `error`, `warning`, `suggestion`, `silent`, and `none`.
Use `none` to disable the rule. See [configuration](../CONFIGURATION.md).

## When to suppress

Suppress when the type parameter is fully explained elsewhere in the comment
and your documentation format requires an empty `<typeparam>` element. Otherwise,
add useful text or remove the empty element if type-parameter coverage is not required.
