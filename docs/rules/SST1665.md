# SST1665 — Documented exceptions should describe what triggers them

| Item | Value |
| --- | --- |
| Category | Documentation |
| Severity | Warning |
| Code fix | No (only the author knows the condition) |
| Default | Enabled |

## Cause

An `<exception>` element names a type but carries no prose saying what makes the member throw it.

```csharp
// 👎 reported — names the type, says nothing about when it fires
/// <summary>Reads a slice of the buffer.</summary>
/// <param name="count">The number of items to read.</param>
/// <exception cref="ArgumentOutOfRangeException"></exception>
public void Read(int count)

// 👎 also reported — the self-closing form has nowhere to put a reason
/// <exception cref="ArgumentNullException" />
```

## Rule description

The type name is the part a caller can already guess. What they cannot guess is the *condition*: which
argument was wrong, which state the member was in, what they should have checked first. An element that
stops at the `cref` sends the reader into the method body — the one thing the documentation existed to
spare them.

An empty element is also worse than a missing one. Anything that measures exception-documentation
coverage — including this package's own SST1662 — sees the element and counts the exception as described,
so the gap is recorded as done and never comes back.

The rule reports an `<exception>` element that:

- is a **top-level element** of the member's documentation comment. An `<exception>` written inside
  `<remarks>` or `<example>` is prose *about* exceptions, not the member's exception contract, and the
  documentation pipeline does not read it as one either;
- carries a **`cref`**, so the diagnostic can name the type it is asking you to explain. A malformed
  `<exception>` with no `cref` is left to the compiler's documentation diagnostics; and
- contains **neither prose nor a nested element**. An element whose content is a `<paramref>` or an
  `<inheritdoc/>` is someone describing the trigger by reference rather than leaving it blank, so it is
  left alone.

This is the complement of [SST1662](SST1662.md), which reports the opposite gap: a member that throws a
type its documentation never mentions.

## How to fix violations

Say what the caller did to earn the throw. Name the argument and the condition, not the type again:

```csharp
/// <summary>Reads a slice of the buffer.</summary>
/// <param name="count">The number of items to read.</param>
/// <exception cref="ArgumentOutOfRangeException">
/// <paramref name="count"/> is negative, or greater than the number of items remaining.
/// </exception>
public void Read(int count)
```

If the exception turns out not to be thrown at all, delete the element instead — an inaccurate exception
contract is worse than none.

### Suppressing it

Where an exception genuinely needs no explanation, turn the rule off in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.SST1665.severity = none
```

## Performance

The rule runs on the documentation elements the compiler already parsed, and rejects a non-`exception`
element on a name comparison. The content scan stops at the first non-whitespace character, and the `cref`
is rendered to text only once a violation is certain — so a comment with no empty `<exception>` element
allocates nothing.
