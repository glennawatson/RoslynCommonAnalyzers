# SST1701 — Combine extension blocks for the same receiver type

| Item | Value |
| --- | --- |
| Category | Extensions |
| Default severity | Warning |
| Enabled by default | Yes |
| Code fix | No |
| Applies to | C# 14 extension blocks |

## Cause

A class declaration contains more than one `extension` block for the same receiver type, the type
named after `extension`. Keeping those members together makes them easier to find.

The receiver type, receiver modifiers, and generic `where` clauses must match as written. Different
receiver variable names do not prevent a report. Different type spellings, such as `string` and
`System.String`, are treated as different types. Blocks with different constraints or different
passing modes, such as `in T` and `T`, are not reported as duplicates. Separate partial class
declarations are not compared.

## Example

Before:

```csharp
public static class StringExtensions
{
    extension(string text)
    {
        public bool IsEmpty => text.Length == 0;
    }

    extension(string other)
    {
        public int Size => other.Length;
    }
}
```

After:

```csharp
public static class StringExtensions
{
    extension(string text)
    {
        public bool IsEmpty => text.Length == 0;
        public int Size => text.Length;
    }
}
```

## How to fix violations

Move the members into one block and remove the duplicate block. Update uses of the receiver variable
if the blocks gave it different names, as with `other` and `text` above.

There is no automatic code fix.

## Configuration

There are no rule-specific options. The default severity is `warning`. To report violations as errors:

```ini
[*.cs]
dotnet_diagnostic.SST1701.severity = error
```

Allowed severities are `none`, `silent`, `suggestion`, `warning`, and `error`.

## When to suppress

Suppress when separate blocks form useful groups with their own documentation or conditional
compilation. Do not merge blocks if doing so changes which members are available.
