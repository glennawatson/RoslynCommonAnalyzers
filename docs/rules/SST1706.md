# SST1706 — Avoid declaring extension members on a broad receiver type

| Item | Value |
| --- | --- |
| Category | Extensions |
| Default severity | Warning |
| Enabled by default | Yes |
| Code fix | No |
| Applies to | Classic extension methods and C# 14 extension blocks |

## Cause

An extension block or classic extension method uses `object`, `System.Object`, or `dynamic` as its
receiver type. A classic extension method is also reported when its receiver is a method type
parameter with no `where` clause, such as `this T value` in `Identity<T>`.

An extension on `object` can appear in completion lists for every type. Use a specific type or
interface when the operation only makes sense for those values.

The rule recognises the three type spellings above. Aliases and `global::System.Object` are not
reported. The unconstrained-type-parameter check applies only to classic extension methods;
a `where` clause prevents that report.

## Example

Before:

```csharp
public static class ObjectExtensions
{
    extension(object value)
    {
        public bool IsNull => value is null;
    }
}
```

After keeping the operation as a static helper:

```csharp
public static class ObjectHelpers
{
    public static bool IsNull(object value) => value is null;
}
```

## How to fix violations

Choose a more specific receiver type, add an appropriate generic constraint, or make the operation
a plain static helper. Update callers to use the chosen API, such as `ObjectHelpers.IsNull(value)`.

There is no automatic code fix.

## Configuration

There are no rule-specific options. The default severity is `warning`. To report violations as errors:

```ini
[*.cs]
dotnet_diagnostic.SST1706.severity = error
```

Allowed severities are `none`, `silent`, `suggestion`, `warning`, and `error`.

## When to suppress

Suppress when the operation is deliberately useful for every type and exposing it as an extension
is part of your API design, such as a shared assertion helper.
