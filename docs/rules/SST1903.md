# SST1903 — Do not lock on a newly-created object

| Item | Value |
| --- | --- |
| Category | Concurrency |
| Default severity | Warning |
| Enabled by default | Yes |
| Code fix | No |

## Cause

A `lock` creates its target with `new`, or targets a local initialized with `new` that is not reassigned or shared. Each call gets a different object, so the lock does not stop callers from running the protected code at the same time.

## What is not reported

A local initialized from a field, property, parameter, or method call is excluded. The rule also leaves a fresh local alone when it is passed as an argument, returned, assigned elsewhere, or used by a lambda or local function. These exclusions do not prove that the locking is safe.

## How to fix violations

Store a dedicated lock object in a private readonly field and use it for every operation protecting the same state.

Reported:

```csharp
public class Counter
{
    private int _count;

    public void Increment()
    {
        object gate = new();
        lock (gate) { _count++; }
    }
}
```

Corrected:

```csharp
public class Counter
{
    private readonly object _gate = new();
    private int _count;

    public void Increment()
    {
        lock (_gate) { _count++; }
    }
}
```

Writing `lock (new object())` has the same problem. Use a static lock field when the protected state is static. If no state is shared between callers, remove the unnecessary lock.

There is no automatic code fix.

## Configuration

There are no rule-specific options. Set the severity in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.SST1903.severity = warning
```

Values are `error`, `warning` (default), `suggestion`, `silent`, and `none`.

## When to suppress

Suppress for a test or benchmark that deliberately measures a lock no other thread can acquire. In application code, use a shared lock object or remove the lock.
