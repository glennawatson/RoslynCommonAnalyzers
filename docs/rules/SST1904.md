# SST1904 — Do not lock on a non-readonly field

| Item | Value |
| --- | --- |
| Category | Concurrency |
| Default severity | Warning |
| Enabled by default | Yes |
| Code fix | Yes, for some fields |

## Cause

A `lock` targets a field declared in the same type, and that field is neither `readonly` nor `const`. Both instance and static fields are checked.

Public, protected, and protected internal fields are excluded; [SST1901](SST1901.md) reports those. Properties, locals, parameters, and inherited fields are not reported here.

Replacing the field's object can let one thread lock the old object while another locks the replacement. Both threads can then change the same state at once.

## How to fix violations

Make the field `readonly` so it cannot be replaced after initialization or construction.

Reported:

```csharp
public class Counter
{
    private object _gate = new();
    private int _count;

    public void Increment()
    {
        lock (_gate) { _count++; }
    }
}
```

Corrected:

```csharp
public class Counter
{
    private readonly object _gate = new();
    private int _count;

    public void Increment()
    {
        lock (_gate) { _count++; }
    }
}
```

## Code fix

**Make the lock field readonly** inserts `readonly` and formats the field declaration. It keeps the initializer and lock statements.

The fix is not offered for a declaration containing multiple fields, or when it finds an assignment to the field outside a constructor. Split a multi-field declaration before fixing it. If the object must be replaced later, review how all callers coordinate that change.

On .NET 9 with C# 13 or later, [PSH1300](PSH1300.md) can help change an eligible dedicated lock field to `System.Threading.Lock`.

## Configuration

There are no rule-specific options. Set the severity in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.SST1904.severity = warning
```

Values are `error`, `warning` (default), `suggestion`, `silent`, and `none`.

## When to suppress

Suppress at the reported lock statement only when a separate synchronization mechanism ensures that replacing the field cannot overlap with any use of the old lock object.
