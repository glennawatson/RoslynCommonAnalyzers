# SST2101 — Use an explicit collection expression

| Item | Value |
| --- | --- |
| Category | CollectionExpressions |
| Severity | Warning |
| Code fix | Yes |
| Default | Disabled (opt-in); C# 12 or later |

## Cause

A non-empty array or standard collection initializer has a supported explicit target.

```csharp
int[] values = new[] { 1, 2, 3 };
```

## Rule description

The equivalent collection expression is `[1, 2, 3]`. Dictionary-style multi-argument
elements and targetless `var` initializers are excluded. The rule is opt-in because
target typing can affect overload resolution.

## What is not reported

An argument a generic call infers a type argument from. A collection expression has no type of its
own — it takes one from its target — so where the target is a method type parameter, the target type
the compiler reports was inferred from this very expression. Removing the creation takes the only
evidence inference had, and the call stops compiling with CS0411 or CS0311:

```csharp
Observable.Return(new byte[] { 1, 2, 3 });   // not reported — Return<T>(T) infers T from the argument
Assert.That(x).IsEquivalentTo(new byte[] { 1, 2, 3 });
```

A type parameter the receiver already fixed is fine, since nothing needs inferring:

```csharp
List<byte[]> sink = [];
sink.Add(new byte[] { 1, 2, 3 });   // reported — Add's T is bound by the list
```

## How to fix violations

Replace the creation and initializer braces with a collection expression. The provided
code fix does this automatically.
