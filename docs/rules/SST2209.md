# SST2209 - Remove a no-op null-forgiving operator

A null-forgiving operator should be removed when it is applied to a value that cannot be null.

## Example

```csharp
var value = 1;
return value!;
```

Use:

```csharp
var value = 1;
return value;
```

## What is reported

Only operands that cannot be null whatever the surrounding code did:

- a **non-nullable value type**, where nullability never applied in the first place;
- an expression that **creates the value it yields** — `new T(...)`, `new()`, `new[] { ... }`, a collection
  expression, or an anonymous object;
- a value the language guarantees is present — a literal, an interpolated string, `typeof(T)`, `this`, `base`.

## What is not reported

Everything else, including every reference-typed call, member access, local, parameter, and field — even
where the suppression looks redundant.

```csharp
(JsonConverter)Activator.CreateInstance(converterType)!   // kept: the call returns object?
interfaceType.FullName!                                   // kept: the property returns string?

string value = MayReturnNull();
Use(value!);                                              // kept: flow analysis says value may be null here
```

The operand's own nullable state cannot decide this. Nullable analysis applies the suppression to the
operand itself, so the semantic model reports it as not-null in every case — including the load-bearing one,
where removing the `!` is exactly what produces a warning. Reporting on that signal removes the suppressions
that are doing work, and the code stops compiling under `TreatWarningsAsErrors`, so the rule stays silent
wherever it cannot prove the operand is non-null by construction.

A suppression on `null`, `default`, or `default(T)` is also left alone: there the `!` is how a deliberate
null is written into a non-nullable slot.
