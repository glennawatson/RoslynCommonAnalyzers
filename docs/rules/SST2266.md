# SST2266 — Inline a local that is read once

| Item | Value |
| --- | --- |
| Category | ModernSyntax |
| Severity | Warning |
| Code fix | Yes (supports Fix All) |
| Default | Disabled (opt-in) |

## Cause

A local is assigned once and read exactly once, and its initializer can be inlined into that one use.

```csharp
var name = _value;
return name;
```

## Rule description

A local that is used a single time asks the reader to carry a name from its declaration to one downstream use.
Inlining the initializer removes the hop.

```csharp
return _value;
```

Whether an intermediate local reads better than the inlined expression is a house-style call — a well-named
temporary is often kept on purpose — so the rule ships **disabled**. Enable it in `.editorconfig` for a
codebase that prefers to inline single-use locals.

The rule only reports when inlining is provably behaviour-preserving:

- **The initializer is side-effect-free.** It reads state without invoking a method, allocating, awaiting, or
  mutating — a literal, an identifier, a member access, a cast, or an operator expression over those. A local
  initialized by a call (`var x = Compute();`) is left alone, because moving the call would move its effect.
- **The declaration converts nothing.** The initializer's own type is the local's type. A declaration that
  widens to a base type or an interface, boxes a value, promotes a number, or picks a delegate for a method
  group is applying a conversion that the use site would not, so inlining would silently rebind the use.
- **The initializer is narrower than the threshold.** Past a configurable width the expression is the harder
  read, and the name has earned its place. See [Configuration](#configuration).
- **The single read immediately follows the declaration.** With nothing between the declaration and the use,
  no intervening statement can change the value the initializer would read.
- **Nothing side-effecting runs before the read in that statement.** If the use statement evaluates a call or
  assignment before reaching the read — `return Side() + value;` — the initializer is not moved there, because
  that would reorder the side effect relative to the read.
- **The local is a plain, uncaptured read.** It is not captured by a lambda or local function, not aliased by
  `ref`/`out`/`in`, and not written after its declaration.
- **A read inside a loop only qualifies for a leaf initializer.** The declaration evaluates once; a read in a
  loop body runs every iteration. See [Reads inside a loop](#reads-inside-a-loop).
- **Every read can be seen.** A block holding an inactive `#if` region is left alone entirely. The identifiers
  in that region are trivia rather than syntax nodes, so they cannot be counted — and a local read once here
  but several times there would lose its declaration for every other build configuration.

## What is not reported

```csharp
var value = Compute();          // not reported — the initializer has side effects
return value;

var value = a;                  // not reported — read more than once
return value + value;

var value = a;                  // not reported — the use is not adjacent
DoSomething();
return value;

var value = a;                  // not reported — captured by a lambda
return () => value;

var options = _options;         // not reported — the other configuration reads it too
#if NET8_0_OR_GREATER
return Resolve(options, options.Resolver);
#else
return Resolve(options);
#endif
```

### Declarations that convert

A local whose declared type is not the initializer's own type exists to apply that conversion. Inlining drops
it, and the use site binds against the initializer's type instead — a different member set, a different
overload, or nothing that compiles.

```csharp
IAppBuilder builder = reactiveBuilder;   // not reported — widening to reach IAppBuilder's members
builder.Build();                         // inlined, this would bind to a member that shadows it

Func<int> handler = Compute;             // not reported — the declaration picks the delegate
Register(handler);                       // inlined, a bare method group re-runs overload resolution

object boxed = _count;                   // not reported — the declaration is what boxes
Write(boxed);                            // inlined, an overload taking int would win instead

int zero = default;                      // not reported — a bare 'default' has no type of its own
Write(zero);                             // inlined against overloads, this no longer compiles
```

An identity declaration — `var`, or an explicit type that matches — is still reported, because there is no
conversion to lose.

### Reads inside a loop

A declaration evaluates its initializer once. A read in a loop body runs on every iteration, so inlining
anything that costs something turns one evaluation into many — a worse program than the local it replaced.

```csharp
var count = Items.Count;        // not reported — inlined, the property would be read per iteration
foreach (var value in values)
{
    total += count;
}
```

A leaf initializer — a literal, an identifier, `typeof` — costs the same either way, so it is still reported.

```csharp
var step = 2;                   // reported — re-reading a literal costs nothing
foreach (var value in values)
{
    total += step;
}
```

### Initializers that are wider than the threshold

```csharp
// not reported by default — the initializer is wider than 40 characters
var empty = default(EquatableArray<PropertyPathSegment>);
return empty.Equals(other);
```

## How to fix violations

The code fix replaces the reference with the initializer and removes the declaration statement. An operator
expression is wrapped in parentheses only where a neighbouring operator could otherwise bind into it; landing
in an argument, a `return`, an initializer, or the right of an assignment, it is spliced in bare.

```csharp
// before
var sum = a + b;
return sum * 2;

// after
return (a + b) * 2;

// before
var sum = a + b;
return Use(sum);

// after
return Use(a + b);
```

Each inline is offered on its own. Inlining one local can leave the one before it single-use as well, so the
rule reports again on the next pass — repeat until it goes quiet. The width threshold is what keeps that chain
short: without it, a run of wide initializers collapses into one expression that repeats every one of them.

## Enabling the rule

The rule is off by default. Turn it on in `.editorconfig`:

```ini
[*.cs]
dotnet_diagnostic.SST2266.severity = warning
```

## Configuration

```ini
# Rule-specific
stylesharp.SST2266.max_initializer_length = 40

# Project-wide
stylesharp.max_initializer_length = 40
```

| Option | Values | Default | Effect |
| --- | --- | --- | --- |
| `max_initializer_length` | positive integer | `40` | The widest initializer, in characters, still worth inlining. |

Raise it to inline longer expressions, or lower it to keep the rule to the shortest initializers — the ones
where the name really was only a hop. A non-numeric or non-positive value keeps the default.

## Performance

The rule matches the declaration shape, checks the initializer's purity and measures its width syntactically
before it resolves the local or scans for its references, so an ordinary declaration pays almost nothing. The
threshold is parsed once per file.
