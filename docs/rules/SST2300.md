# SST2300 — Implement the disposal pattern correctly

| Item | Value |
| --- | --- |
| Category | Design |
| Severity | Warning |
| Code fix | Partial |
| Default | Enabled |

## Cause

A class implements `IDisposable` but is missing part of its cleanup pattern. For the class that
first implements the interface, the rule reports the first matching problem:

1. An unsealed class has no `void Dispose(bool)` overload.
2. Its `Dispose(bool)` overload is public.
3. It has that overload, but `Dispose()` does not call `Dispose(true)`.
4. It declares a finalizer, but `Dispose()` does not call `GC.SuppressFinalize(this)`.

A derived class is checked for a public, parameterless `Dispose()` that hides the base method
instead of overriding it. Cleanup in the hidden method can be missed when callers use the base type.

A sealed class with only `Dispose()` and no finalizer needs no extra pattern. Records, structs,
and types implementing only `IAsyncDisposable` are excluded. An abstract `Dispose()` has no body
to check, but an unsealed class declaring it still needs the overload.

## Example

Bad:

```csharp
using System;

public class Connection : IDisposable
{
    public void Dispose()
    {
    }
}
```

Corrected when derived classes need to add cleanup:

```csharp
using System;

public class Connection : IDisposable
{
    public void Dispose()
    {
        Dispose(true);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (disposing)
        {
            // Dispose owned managed resources here.
        }
    }
}
```

## How to fix violations

Use `protected virtual Dispose(bool)` to let derived classes extend cleanup. If inheritance is
unnecessary, sealing the class allows a plain `Dispose()` instead.

A finalizer runs when the garbage collector reclaims an object. Add one only when the type needs
to release unmanaged resources directly. It should call `Dispose(false)`; cleanup of managed
objects belongs in the `disposing == true` path. After normal disposal, `GC.SuppressFinalize(this)`
prevents the finalizer from repeating the cleanup.

## Code fix

Two repairs have a fix, both with Fix All:

- Add `GC.SuppressFinalize(this)` at the end of `Dispose()`. An expression body becomes a formatted
  block. The call uses `System.GC` when needed. Comments attached to the removed `=>` or semicolon
  can be lost.
- Change public `Dispose(bool)` to `protected virtual`, or to `private` on a sealed class. Its body
  stays in place. Calls from outside the class can stop compiling after the access change.

There is no code fix for a missing overload, a missing `Dispose(true)` call, or a hidden `Dispose()`.
Those repairs require you to choose where cleanup belongs. Fixing one problem can reveal the next.

## Configuration

There are no rule-specific options. The default severity is `warning`; this repository sets it
to `error`:

```editorconfig
[*.cs]
dotnet_diagnostic.SST2300.severity = error
```

Accepted values are `none`, `silent`, `suggestion`, `warning`, and `error`.
See [Configuration](../CONFIGURATION.md).

## When to suppress

Suppress for an established disposal contract that you cannot change compatibly, after checking
that both base and derived resources are released. Do not suppress a missing cleanup call merely
because tests do not use the finalizer path.
