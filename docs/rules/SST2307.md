# SST2307 — Generic method type parameters should be inferable from the parameters

| Item | Value |
| --- | --- |
| Category | Design |
| Severity | Warning |
| Code fix | No |
| Default | Enabled |

## Cause

A generic method visible outside its assembly declares a type parameter that appears in none of its
parameter types. Callers must supply the type arguments themselves. A return type or a `where`
constraint does not let C# infer them.

## How to fix violations

If the method works on a value, accept that value as a parameter.

Bad:

```csharp
public static class Registry
{
    public static void Register<TService>() { }
}
```

Corrected:

```csharp
public static class Registry
{
    public static void Register<TService>(TService service) { }
}
```

A type parameter also counts when it appears inside a parameter type, such as `T[]`, `List<T>` or
`Func<T>`. If the operation needs a type rather than a value, consider accepting `System.Type`, or
keep the generic method and suppress the rule.

There is no code fix.

## What is not reported

- Methods that are not visible outside the assembly, including public methods inside internal types.
- Overrides and interface implementations. The interface or base declaration can still be reported.
- Type parameters declared on a class or struct rather than on a method.
- Generated code.

## Configuration

The default severity is `warning`. To report violations as errors:

```ini
[*.cs]
dotnet_diagnostic.SST2307.severity = error
```

Use `none` to disable the rule. There are no rule-specific options.

## When to suppress

Suppress it for factories, serializers or service resolvers where the caller is meant to choose the
type explicitly, such as `Create<Order>()`. Do not add an unused value parameter merely to satisfy
the rule.
