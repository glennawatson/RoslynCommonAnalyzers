# SST2318 — Members should not have identical bodies

| Item | Value |
| --- | --- |
| Category | Design |
| Severity | Warning |
| Code fix | No |
| Default | Disabled |

## Cause

Two methods in the same type declaration have matching bodies and the same written parameter types
and modifiers. Whitespace and comments do not affect the match. Each method after the first match
is reported.

The duplicate can be a copy-and-paste mistake or intentional shared behavior. Review which one it is
before changing the code.

## How to fix violations

Correct the duplicated calculation if it is wrong. If it is intentional, put the shared behavior
in one method and call it from the other.

Bad:

```csharp
public sealed class Calculator
{
    public int First(int a, int b)
    {
        var sum = a + b;
        return sum * 2;
    }

    public int Second(int a, int b)
    {
        var sum = a + b;
        return sum * 2;
    }
}
```

Corrected, when both methods should do the same work:

```csharp
public sealed class Calculator
{
    public int First(int a, int b)
    {
        var sum = a + b;
        return sum * 2;
    }

    public int Second(int a, int b) => First(a, b);
}
```

There is no code fix.

## What is reported

Block bodies must contain at least two statements. Expression bodies can also be reported,
including calculations and method calls. Expression bodies consisting only of a literal, a name,
a member access, `throw` or `default` are ignored.

Parameter names are ignored in the parameter list, but names used in the body still need to match.
Different written parameter types or modifiers prevent a match, including `int` versus `System.Int32`
and `int` versus `ref int`. Methods in different parts of a partial type are not compared with each other.

Properties, constructors, methods without bodies and generated code are not reported.

## Configuration

The rule is disabled by default. To enable it as an error:

```ini
[*.cs]
dotnet_diagnostic.SST2318.severity = error
```

Use `warning` for a warning or `none` to disable it. There are no rule-specific options.

## When to suppress

Suppress a deliberate duplicate when sharing the implementation would obscure the methods' separate
contracts or change dispatch through virtual methods. Keep the rule disabled if such duplication is
common in the codebase.
