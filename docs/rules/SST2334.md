# SST2334 — Give a public type a debugger-display attribute

| Item | Value |
| --- | --- |
| Category | Design |
| Severity | Warning |
| Code fix | Yes (add a `[DebuggerDisplay]` skeleton) |
| Default | Disabled (opt-in) |

## Cause

A publicly visible class, struct, or record that has state worth showing carries no
`[System.Diagnostics.DebuggerDisplay]` attribute.

```csharp
public class Money   // SST2334
{
    public int Amount { get; set; }
}
```

## Rule description

In the debugger, a type with no display attribute shows as its bare type name and nothing else, so a watch
window or a collection of instances is opaque until each one is expanded. A `[DebuggerDisplay]` string surfaces
the one or two members that identify an instance at a glance, which pays for itself the first time you scan a
list of them.

This is an opinionated, heavy nudge that would otherwise fire on nearly every public type, so it is **disabled
by default** and opt-in through `.editorconfig`. The rule resolves the attribute type in the compilation and
stays silent when it is absent, so the fix it offers always has something to add.

### A type needs something to show

A type with no state cannot be given a display string that says more than the debugger already does: the only
thing left to name is `ToString()`, and a type that does not override it renders as its own type name either
way. Reporting there asks for an attribute whose whole effect is to restate the status quo, so the rule asks
first for one of:

- **a declared instance field or property**, of *any* accessibility. A display string is evaluated in the
  type's own context, so `[DebuggerDisplay("{_value}")]` over a private field is as valid as one naming a
  public property — requiring `public` would silence exactly the wrapper types the attribute helps most; or
- **a `ToString()` override**, which is what makes the fallback display string mean something.

Statics and constants describe no instance and do not count, and neither does anything the compiler generated
rather than the author writing it — a record's `EqualityContract` and synthesized `ToString`, an
auto-property's backing field. So a marker class, a class of constants, and an empty `record Nothing();` all
stay clean, while `record Money(int Amount)` is reported on its declared `Amount`.

An **overriding property** does not count either. It answers a base class's contract rather than describing
this instance, and it is usually identical for every instance of the type, so a behavioural class whose only
property is an override has nothing to put in a watch window — naming it is precisely the useless suggestion
this gate exists to prevent. Measured against this repository's own analyzer sources, that one exclusion is
what takes the rule from 436 reports over 726 files to none: every one of those types is a stateless class
whose only property is an overridden `SupportedDiagnostics`. An overridden `ToString` is the exception, and it
qualifies on its own terms above.

## Opting in

```ini
[*.cs]
dotnet_diagnostic.SST2334.severity = warning
```

## What is reported

- An externally visible class or struct (including a record) that declares instance state, or overrides
  `ToString()`, and has no `[DebuggerDisplay]` attribute.

## What is not reported

- A type that already carries the attribute.
- An `internal` or otherwise non-externally-visible type.
- A `static` class, which has no instances to display.
- A type with nothing to name: no declared instance field or property and no `ToString()` override.
- A type whose only property overrides a base member, which describes the contract rather than the instance.
- A write-only property or an indexer, neither of which can be dropped into a display string by name.

## How to fix violations

The code fix adds a `[DebuggerDisplay]` skeleton that leads with the type's own name and then names the best
member the type has to identify an instance by — its first public property, else any other readable property,
else its first field — falling back to `ToString()` when it has none of those:

```diff
+[System.Diagnostics.DebuggerDisplay("Money: {Amount}")]
 public class Money
 {
     public int Amount { get; set; }
 }
```

The name prefix is there because a display string *replaces* the type name the debugger would otherwise show.
Without it, a watch window or a mixed collection is a column of bare values — `42`, `"abc"`, `0` — with nothing
saying what each one is. A generic type is prefixed with its bare name (`Box: {Value}`), since the debugger
shows the constructed type separately.

The generated string is a starting point — refine it to the members that best identify an instance.

## Performance

The clean path is an attribute scan on a type that is already externally visible, and the member scan behind it
runs only for a type that got past both; a project whose framework has no debugger-display attribute never
registers the rule at all.
