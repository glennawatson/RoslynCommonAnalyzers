# SST2336 — An attribute type should declare where it can be applied

| Item | Value |
| --- | --- |
| Category | Design |
| Severity | Warning |
| Code fix | No |
| Default | Enabled |

## Cause

A concrete attribute type declares no `[AttributeUsage]`.

```csharp
// 👎 reported
public sealed class MarkerAttribute : Attribute
{
}

// 👍
[AttributeUsage(AttributeTargets.Method)]
public sealed class MarkerAttribute : Attribute
{
}
```

## Rule description

Without `[AttributeUsage]` an attribute defaults to `AttributeTargets.All`, single-use, and non-inherited.
Almost no attribute means all of that.

One written for methods can be put on a parameter, a field, or an assembly and the compiler will not object —
so the mistake surfaces as the attribute quietly doing nothing, rather than as a build error. Declaring the
usage turns every wrong placement into a compile error, and it is the only way to say that an attribute may
repeat (`AllowMultiple`) or that derived types should inherit it (`Inherited`).

### What is reported

- A non-abstract class deriving from `Attribute` with no `[AttributeUsage]` anywhere on its own inheritance
  chain.

### What is not reported

- An abstract attribute base: the concrete attribute deriving from it is where the targets belong.
- A type whose base attribute already declares the usage, which it inherits.
- Whatever the framework declares on `Attribute` itself — that is the default every attribute already has,
  not a decision this type made.

## How to fix violations

Add `[AttributeUsage]` naming the targets the attribute is meant for. There is no code fix, because which
targets are right is the decision the rule is asking you to make.

## Performance

`Attribute` and `AttributeUsageAttribute` are resolved once per compilation and the rule registers nothing
when either is absent, so a project with no attributes pays a single lookup.
