# SST2450 - Debug.Assert conditions must not have side effects

| Item | Value |
| --- | --- |
| Category | Correctness |
| Severity | Warning |
| Code fix | No |
| Default | Enabled |

## Cause

The first argument of `System.Diagnostics.Debug.Assert`, normally the condition, contains an assignment, an increment or decrement, or a call with a recognized state-changing method name. A side effect is work that changes program state, such as removing an item from a list.

When `DEBUG` is not defined, the compiler removes the call and does not evaluate its arguments. This is usual for Release builds. Any required work inside the condition therefore disappears from those builds.

The recognized method names are `Add`, `Remove`, `Pop`, `Dequeue`, `MoveNext`, `TryAdd`, `TryRemove`, `TryTake`, `TryPop`, `TryPush`, `TryDequeue`, and `TryUpdate`, called through a member access such as `items.Remove(value)`.

Calls such as `Contains`, `TryGetValue`, and ordinary predicates are not reported. Neither are calls reached through `?.`, `Trace.Assert`, or your own `Assert` methods. The rule does not prove that an unreported call is free of side effects. It also reports recognized names on custom or immutable types, even when those methods do not change state.

## Example

Incorrect:

```csharp
using System.Collections.Generic;
using System.Diagnostics;

public class Example
{
    public void Remove(List<int> items, int value)
    {
        Debug.Assert(items.Remove(value));
    }
}
```

Correct:

```csharp
using System.Collections.Generic;
using System.Diagnostics;

public class Example
{
    public void Remove(List<int> items, int value)
    {
        bool removed = items.Remove(value);
        Debug.Assert(removed);
    }
}
```

## How to fix violations

Move required work before the assertion and check its result. If it appears behind `&&`, `||`, or `?:`, preserve the condition that decides whether the work should run.

There is no code fix because moving or removing the work requires a decision about the intended behavior in every build.

## Configuration

There are no rule-specific options. The rule is enabled as a warning by default; this repository sets its severity to `error`.

```editorconfig
[*.cs]
dotnet_diagnostic.SST2450.severity = warning
```

Severity values are `none`, `silent`, `suggestion`, `warning`, and `error`.

## When to suppress

Suppress when the work is intentionally for debug checks only and release behavior does not depend on it. Suppression is also reasonable for a reported method that you have verified does not change state, such as an immutable collection operation.
