# SST2499 — Read the exit status rather than the exit code when a process can be signalled

| Item | Value |
| --- | --- |
| Category | Correctness |
| Severity | Warning |
| Code fix | No |
| Applies to | Frameworks offering `Process.WaitForExitStatus` |

## Cause

`Process.ExitCode` is read in the same member as a `WaitForExit` or `WaitForExitAsync` call.

```csharp
process.WaitForExit();
return process.ExitCode;
```

## Rule description

On Unix a process killed by a signal has no exit code of its own. `ExitCode` reports a value derived
from the signal number instead — in the same range a process can return deliberately — so code
branching on it cannot tell "the child chose to fail with 137" from "the kernel killed the child with
SIGKILL".

That difference usually decides what happens next. An out-of-memory kill is worth retrying elsewhere
or reporting as infrastructure failure; a deliberate exit code 137 is the program's own answer.
Conflating them hides the cause exactly when it matters.

```csharp
// 👍
ProcessExitStatus status = process.WaitForExitStatus();

if (status.Signal is { } signal)
{
    // Terminated by the kernel; the exit code would have been misleading.
}
```

## What is not reported

- An `ExitCode` read with no wait call in the same member. That is reading a status the code got from
  somewhere else, not deciding what a child process's result meant.
- An `ExitCode` member on any type other than `System.Diagnostics.Process`.
- Anything at all when the referenced framework does not offer `WaitForExitStatus`. The rule resolves
  the replacement in the analyzed compilation and stays silent when it is absent, so it never reports
  a diagnostic that cannot be acted on.

## How to fix violations

Replace the `WaitForExit()` plus `ExitCode` pair with `WaitForExitStatus()` (or
`WaitForExitStatusAsync()`), and branch on the returned status rather than on a bare integer. Where
you only need to know whether the process succeeded, test the status rather than comparing the exit
code to zero.
